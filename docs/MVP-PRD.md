# hi-resume MVP PRD

状态：Draft
版本：0.2
更新日期：2026-08-21
产品形态：个人本地应用（第一用户为作者本人）

## 1. 产品概述

hi-resume 是一个本地优先的个人简历管理工具，同时管理**简历内容**和**投递进度**。

用户维护一个素材池和一份主简历，再针对不同公司职位创建岗位版本。岗位版本默认继承主简历的内容选择，调整以「选哪些条目、按什么顺序、隐藏哪些模块」为主，只有少量字段需要改写文字。每个岗位版本同时是一条投递记录。

产品交互参考 FlowCV 的表单编辑与实时预览，但不依赖在线账户或付费额度。

## 2. 背景与问题

面向不同 JD 投递时，需要调整的通常是：

- 展示哪些项目和工作经历，以及它们的顺序；
- 每条经历下展示哪几条 bullet；
- 技能的取舍和排序；
- 简历展示模块（区块）的取舍和顺序；
- 个人简介的措辞和求职方向。

现有工具的问题：

- FlowCV 免费版只能维护一份简历，针对新 JD 的调整会**破坏性覆盖**上一次的调整结果，无法保留多个针对性版本；
- 直接复制多份文件，主简历改进后旧版本不会同步；
- 素材库和简历是两份割裂的文档，把素材换进简历靠复制粘贴；
- 投递进度记在另一个地方（表格或备忘录），和简历版本对不上号。

## 3. 产品目标

### 3.1 MVP 目标

用户可以在本地完成以下闭环：

1. 从零手动建立一份可投递的主简历；
2. 针对一个 JD 创建岗位版本；
3. 通过选择、排序、隐藏和少量改写完成针对性调整，实时看到排版；
4. 导出可投递 PDF；
5. 记录这次投递的状态和后续进展；
6. 打开应用即可看到所有投递的当前状态；
7. 导出 JSON 备份，重装后可完整恢复。

### 3.2 非目标

MVP 不做：

- 用户注册、登录和云端同步；
- 在线分享和协作评论；
- AI 改写、翻译和 JD 匹配；
- ATS 评分或通过率预测；
- PDF/DOCX 解析导入；
- DOCX 导出；
- 邮件投递、邮箱集成和 JD 网站自动抓取；
- 需要后台进程的定时提醒和通知；
- 多模板市场和自由画布排版。

投递追踪本身在 MVP 范围内，但只做「手动记录 + 打开时看到」这一层。

## 4. 目标用户与典型场景

### 4.1 目标用户

第一阶段只服务作者本人。特征：

- 已经有成熟的简历内容，只是散落在 FlowCV 和 markdown 文档里；
- 高频投递不同职位，每次都要做针对性调整；
- 重视本地数据控制和可迁移备份。

不做面向陌生用户的引导教学，但**空简历的录入体验必须好** —— MVP 的第一次真实使用就是把已有内容手工敲进去，这个过程会直接暴露表单编辑器的所有问题。

### 4.2 核心场景

**场景 A：针对一个 JD 调整并投递**

1. 新建岗位版本，填写公司和职位，粘贴 JD 原文备查；
2. 版本自动继承主简历的全部内容选择；
3. 把最相关的两个项目移到前面，从素材池换进一个主简历里没放的项目；
4. 关掉某个项目下的三条不相关 bullet；
5. 调整技能顺序，隐藏「语言」区块；
6. 改写个人简介；
7. 看预览确认一页装得下；
8. 导出 `公司-职位-姓名.pdf`，把状态标为「已投递」。

**场景 B：跟进投递进度**

1. 打开应用，首页按状态显示所有投递；
2. 看到「3 个投递超过 14 天无进展」；
3. 某家约了一面，把状态改为「面试中」，记一条事件和下次面试时间。

**场景 C：主简历改进后同步**

1. 给某段工作经历写了一条更好的 bullet，加进主简历；
2. 已有岗位版本中，没有手动调整过该条目的版本自动继承这条 bullet；
3. 手动调整过的版本显示提示：主简历此处有更新，可选择接受。

## 5. 核心产品模型

### 5.1 三层结构

```text
条目池 Item Pool
  所有工作经历、项目、bullet、技能、教育等条目，每个有稳定 ID
        │
        ├── 主简历 Master：一份选择清单 + 顺序 → 可直接投递的 1–2 页
        │
        └── 岗位版本 Variant：默认继承主简历的清单，可增删调序 + 少量文字覆盖
                                + 投递元信息与进度
```

条目池不是独立的数据结构，它就是「当前没有被主简历选中的条目」。因此「把素材池里的项目换进这个版本」是一次选择操作，不是复制粘贴。

### 5.2 主简历

主简历是一份**可直接投递的完整简历**，不是超集。它代表「没有特定目标职位时我会投出去的那一份」，可以导出 PDF。

这一点与超集式设计的区别很重要：如果主简历是超集，每个新建的岗位版本都要先删到能投，反而增加工作量。主简历保持可投递状态，岗位版本才能「继承即可用」。

### 5.3 岗位版本

岗位版本 = 内容视图 + 投递记录。

内容侧包含三类调整，优先级从高到低：

1. **选择**：这个版本展示哪些区块、哪些条目、哪些 bullet；
2. **排序**：区块顺序、条目顺序、bullet 顺序；
3. **文字覆盖**：只对区块标题、个人简介、条目标题和 bullet 文本开放。

投递侧包含公司、职位、地点、JD 原文、状态、投递日期、事件记录和下一步动作。

一个岗位版本对应一次投递。要投第二家公司时复制一份版本，而不是让一个版本挂多次投递。

### 5.4 字段与条目状态

需要能表达的状态：

- `inherited`：与主简历一致；
- `adjusted`：本版本调整过（换了选择、改了顺序或改了文字）；
- `hidden`：本版本不展示；
- `upstream-changed`：主简历中对应内容有更新，而本版本已手动调整过，需要用户决定是否接受。

不需要 `orphaned`。主简历移除条目只是把它移回素材池，选用了该条目的岗位版本不受影响。只有从素材池彻底删除条目时才有影响，届时在删除确认中提示被哪些版本使用。

## 6. 功能范围

### 6.1 P0：必须完成

#### A. 本地工作区

- 首次打开创建本地工作区；
- 无账号、无后端、无必需网络请求；
- 自动保存，显示最近保存时间；
- JSON 导入导出，导入前格式校验；
- 数据结构带 `schemaVersion`，导入旧版本时执行迁移或明确报错。

#### B. 区块（Section）管理

区块是简历的展示模块。用户完全掌控简历上出现哪些区块、叫什么名字、以什么顺序排列。

- 内置区块：基本信息、个人简介、工作经历、项目经历、教育经历、技能、语言；
- 新建自定义区块，指定名称和结构（列表型 / 纯文本型）；
- 重命名任意区块，包括内置区块；
- 拖拽调整区块顺序；
- 显示 / 隐藏区块；
- 删除自定义区块。内置区块只能隐藏不能删除，避免误删后无法恢复；
- 主简历和每个岗位版本都可以独立设置区块的顺序、显隐和名称。

区块名称按版本独立是有实际用途的：同一批内容在不同版本里可能叫「项目经历」或「产品案例」。

**操作位置**：左栏和预览两处都能改。

- 左栏区块列表：拖拽排序、显隐开关、重命名、新建自定义区块；
- 预览区：鼠标悬停某个区块时，在区块右上角显示轻量工具条 —— 上移、下移、隐藏、重命名。

预览内的自由拖拽排序不进 MVP。预览是分页文档，跨页拖放的实现成本和出错概率都高，而悬停工具条已经能覆盖绝大多数调整。若实际用下来仍嫌不够直接，再在 P1 补。

#### C. 素材池与条目编辑

每个区块内支持：

- 条目的新增、编辑、删除；
- 条目在主简历中的「选中 / 未选中」切换；
- 条目排序；
- bullet 的新增、编辑、删除、排序；
- 删除条目前确认，并提示被哪些岗位版本使用。

素材池视图：按区块类型浏览所有条目，标明每个条目被主简历和哪些岗位版本使用。

主简历可导出 PDF。

#### D. 岗位版本管理

- 从主简历创建岗位版本；
- 填写公司、职位、地点、备注，可选粘贴 JD 原文；
- 创建、重命名、复制、归档、删除；
- 明确标识当前编辑的是主简历还是某个岗位版本。

#### E. 继承与调整

- 岗位版本默认继承主简历的全部选择与顺序；
- 从素材池向本版本增加条目；
- 从本版本移除条目或 bullet（不影响主简历和其他版本）；
- 本版本独立调整区块、条目和 bullet 顺序；
- 隐藏整个区块、调整区块顺序、在本版本内重命名区块；
- 对个人简介、条目标题和 bullet 文本做文字覆盖；
- 每处调整旁显示「继承中 / 本版本已调整」，并支持一键恢复为主简历内容；
- 主简历新增内容默认流入未调整过的版本；
- 主简历更新了某处而本版本已调整时，显示 `upstream-changed` 提示，由用户决定接受与否。

#### F. 投递追踪

- 每个岗位版本携带状态：`draft / applied / interviewing / offer / rejected / closed`；
- 记录投递日期和下一步动作及其日期；
- 追加事件记录（时间 + 一句话），形成简单时间线；
- 首页按状态分组展示所有投递；
- 打开应用时高亮「已投递超过 N 天无进展」和「下一步动作已到期」；
- 不做邮件集成、不做自动抓取、不做系统通知。

#### G. 编辑器与预览

桌面端三栏布局：

- 左栏：区块列表（可拖拽排序、显隐、重命名）、素材池入口、版本状态；
- 中栏：表单编辑；
- 右栏：A4 实时预览。

最低要求：

- 输入后预览即时更新，且不因刷新丢失输入焦点或内容；
- 支持多行文本与 bullet 列表编辑；
- 预览保持稳定 A4 比例，支持 A4 与 Letter；
- 预览按真实分页显示，一页和多页都要正确。

#### H. 导出

- 浏览器/Chromium 打印为 PDF，文本型内容，不使用整页图片；
- 自动建议文件名 `公司-职位-姓名.pdf`；
- 导出前显示当前岗位版本名称；
- 导出 JSON 完整备份，可重新导入并继续编辑。

#### I. 基础恢复能力

- 最近若干次编辑快照；
- 撤销与重做；
- 删除岗位版本或素材池条目前二次确认。

### 6.2 P1：MVP 后优先考虑

- 主简历与岗位版本差异视图；
- 点击预览定位到对应编辑字段；
- 条目级历史；
- JD 关键词高亮（纯文本匹配，不做 AI 评分）；
- 多语言简历；
- 字体、颜色与间距设置；
- 简单封面信模板；
- Markdown 素材库一次性导入（单向，不做双向同步）；
- 预览区内直接拖拽排序区块与条目；
- 区块级排版选项（技能标签云 / 分组列表 / 单行等）；
- 投递数据的统计视图（投递数、回复率、周期）。

### 6.3 P2：暂不承诺

- AI 改写与 JD 匹配；
- ATS 评分；
- PDF/DOCX 导入；
- DOCX 导出；
- 云同步与多设备；
- 分享链接；
- 一个版本对应多次投递；
- 模板市场。

## 7. 页面与交互

### 7.1 首页：投递看板

首页是每天打开的页面，以投递为主体而非文件列表。

包含：

- 按状态分组的投递卡片：公司、职位、投递日期、距今天数、下一步动作；
- 需要关注的提醒区：超期无进展、下一步动作到期；
- 主简历入口；
- 素材池入口；
- 新建岗位版本；
- 工作区导入导出。

空状态直接指向主简历：

> 先建立你的主简历，之后可以针对不同职位创建版本。

### 7.2 编辑页面

顶部显示：当前版本名称、投递状态、最近保存时间、导出 PDF、返回首页。

字段提示使用用户语言，不暴露 overlay / patch / merge 等技术词：

- 「继承自主简历」；
- 「本版本已调整」；
- 「恢复主简历内容」；
- 「主简历此处有更新」。

### 7.3 素材池页面

按区块类型列出全部条目，每个条目显示被主简历使用与否、被哪几个岗位版本使用。支持在此新增条目、编辑文本、删除。

## 8. 数据模型草案

所有条目必须有稳定 ID，包括 bullet。选择和排序均按 ID 引用，不使用数组下标。

```ts
type Workspace = {
  schemaVersion: number
  pool: ItemPool
  master: ResumeComposition
  variants: ResumeVariant[]
  settings: WorkspaceSettings
}

type ItemPool = {
  sections: Record<SectionId, Section>       // 区块定义（含自定义区块）
  entries: Record<EntryId, Entry>            // 工作/项目/教育/技能等条目
  bullets: Record<BulletId, Bullet>          // 条目下的要点，独立寻址
  basics: Basics                             // 基本信息，不参与选择
}

type Section = {
  id: SectionId
  kind: "basics" | "summary" | "work" | "project"
      | "education" | "skill" | "language" | "custom"
  title: string                              // 默认标题，可被主简历或版本重命名
  layout: "entries" | "text"                 // 列表型或纯文本型
  removable: boolean                         // 内置区块为 false，只能隐藏
}

type Entry = {
  id: EntryId
  sectionId: SectionId
  title: string
  subtitle?: string
  period?: { start: string; end?: string }
  bulletIds: BulletId[]                      // 该条目拥有的全部 bullet
}

// 一份「简历长什么样」的组合，主简历和岗位版本共用
type ResumeComposition = {
  sectionOrder: SectionId[]
  visibleSections: SectionId[]
  sectionTitles: Record<SectionId, string>        // 重命名，缺省用 Section.title
  entrySelection: Record<SectionId, EntryId[]>    // 选中的条目，数组顺序即展示顺序
  bulletSelection: Record<EntryId, BulletId[]>    // 选中的 bullet，数组顺序即展示顺序
  summary?: string
}

type ResumeVariant = {
  id: string
  name: string
  composition: Partial<ResumeComposition>    // 只存与主简历不同的部分
  textOverrides: Record<BulletId | EntryId | "summary", string>
  application: Application                   // 投递侧信息
  createdAt: string
  updatedAt: string
}

type Application = {
  company?: string
  role?: string
  location?: string
  jobDescription?: string
  status: "draft" | "applied" | "interviewing" | "offer" | "rejected" | "closed"
  appliedAt?: string
  nextAction?: { text: string; dueAt?: string }
  events: { at: string; text: string }[]
  notes?: string
}
```

渲染规则：

```text
render(pool, master, variant)
  = resolveComposition(master, variant.composition)
  + applyTextOverrides(variant.textOverrides)
```

`resolveComposition` 逐字段回退：变体没写的字段用主简历的值。这样主简历的新增内容会自动流入未调整过该字段的版本。

导入导出以 JSON Resume 字段作为互操作参考，但内部模型必须保留稳定 ID、选择、排序和投递信息。

## 9. 非功能需求

### 隐私

- 数据默认不离开本机；
- 不加载第三方分析脚本；
- 未来若引入 AI 或外部服务，必须显式开启并说明哪些内容会离开本机。

### 性能

- 输入到预览更新的 P95 延迟低于 100ms；
- 打开含 200 个条目、20 个岗位版本的工作区，首屏低于 1s；
- 自动保存对 IndexedDB 的写入需去抖，并在关闭前强制落盘。

### 可恢复性

- JSON 为可读、可迁移的备份格式；
- 数据结构支持版本迁移；
- 本地存储损坏时可通过 JSON 完整恢复工作区。

## 10. MVP 验收标准

### 主简历闭环

- 从空工作区可以手工建成一份完整主简历并导出 PDF；
- 区块可重命名、排序、显隐，自定义区块可新建和删除；
- 条目与 bullet 可增删改和排序；
- 关闭重开后内容与排版完全一致。

### 版本闭环

- 创建岗位版本不超过 3 次点击，且立即处于可导出状态；
- 岗位版本中的调整不影响主简历和其他版本；
- 恢复某处调整后内容与主简历一致；
- 主简历新增 bullet 后，未调整过该条目的版本自动获得该 bullet；
- 主简历修改已被调整处时，对应版本出现 `upstream-changed` 提示；
- 从素材池删除被使用的条目时，删除确认中列出使用它的版本。

### 追踪闭环

- 每个岗位版本可设置状态、投递日期和下一步动作；
- 首页按状态分组显示全部投递；
- 超期无进展和到期动作在首页可见；
- 状态变更后重开应用仍然保留。

### 输出与数据

- 预览内容与导出 PDF 内容一致；
- PDF 文本可选中复制；
- 导出的 JSON 可重新导入，且导入后与导出前等价；
- 关闭并重开后数据仍在。

### 质量底线

- 一页简历不出现截断；
- 两页简历分页稳定；
- 关键操作有成功、失败与恢复提示；
- 删除操作不可误触完成。

## 11. 实施顺序

按里程碑推进，每个里程碑结束时产物都能真正用起来，而不是等全部做完才第一次使用。

### M1：一份主简历跑通闭环

范围只有主简历，没有岗位版本、素材池和追踪。

- 定义条目池、组合与稳定 ID —— **结构按完整模型建，不因为暂时只有一份简历而简化**；
- 区块管理：新建自定义区块、重命名、排序、显隐；
- 条目与 bullet 的增删改排序；
- 一个模板的 HTML/CSS，含真实分页预览；
- IndexedDB 自动保存；
- PDF 导出与 JSON 导入导出。

两条硬要求：

1. **分页在 M1 解决**，不推到后面；
2. **JSON 导出必须在 M1 就有**。第一次真实使用是手工录入全部内容，这些内容不能被锁死在 IndexedDB 里。

M1 结束的标志：作者本人用它敲完真实主简历，导出的 PDF 可以直接投递。

### M2：素材池与岗位版本

- 素材池视图与条目的选中/未选中；
- 岗位版本的创建、复制、删除；
- 选择、排序、隐藏与文字覆盖；
- 继承回退与 `upstream-changed` 提示。

数据层在此之前即建立可逆操作流，为撤销重做留出接口。

### M3：投递追踪与打磨

- 投递状态、事件与下一步动作；
- 首页投递看板与提醒；
- 撤销重做；
- 打印样式与文件名打磨；
- 关键流程测试；
- 用真实投递验证。

### M4：Markdown 导入

在 M1–M3 的数据结构稳定之后再做，作为独立脚本产出工作区 JSON。放到最后的理由：手工录入一次的成本是固定的几小时，而在结构未定型时写导入器会反复返工。

## 12. 成功指标

个人使用场景下达到以下结果即可进入下一阶段：

- 主简历能完全替代现有 FlowCV 简历，包括排版质量；
- 能同时维护至少 5 个岗位版本，互不干扰；
- 针对新 JD 完成调整并导出的时间低于 15 分钟；
- 新建岗位版本无需任何复制粘贴；
- 主简历改进后，未调整过的部分在各版本中自动生效；
- 所有投递的当前状态可在首页一屏内看清；
- 完整流程不依赖 FlowCV 或其他在线服务。

## 13. 关键风险与决策

### 风险：继承关系难以理解

决策：把模型收窄为「选择 + 排序 + 少量文字覆盖」，不做通用的字段级 patch。界面只出现「继承中 / 本版本已调整 / 恢复主简历内容」，不暴露底层概念。

### 风险：分页与 PDF 排版投入过大

决策：只做一个模板，分页作为 Phase 0 的验收内容而非收尾工作。Web 阶段接受浏览器打印对话框带来的精度损失，等实际影响投递质量时再上 Tauri。

### 风险：追踪功能滑向 CRM

决策：追踪只做「手动记录 + 打开时看到」。任何需要邮箱、爬虫或后台进程的能力一律排除在 MVP 之外。

### 风险：本地数据丢失

决策：自动保存、快照与 JSON 导出全部在 P0，不延后。

### 风险：功能扩张

决策：任何不能直接服务「维护素材、生成针对性版本、导出、记录进展」的功能，默认进入 P1 或 P2。
