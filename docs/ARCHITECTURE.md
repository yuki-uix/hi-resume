# 架构与技术决策

状态：Proposed
版本：0.2
更新日期：2026-08-21

## 1. 总体方向

Web-first 开发，Desktop-first 交付：

- 开发阶段使用 React + TypeScript + Vite；
- 数据层从第一天起与 UI 解耦；
- MVP 以 Web 形态交付并投入真实使用，接受浏览器打印对话框带来的精度损失；
- 当导出精度实际影响投递质量时，再用 Tauri 打包并改用 headless print-to-pdf；
- 核心功能不依赖服务器。

## 2. 推荐技术栈

| 层 | 选择 | 原因 |
|---|---|---|
| UI | React + TypeScript | 适合复杂表单、局部更新和类型约束 |
| 构建 | Vite | 本地开发快，便于后续桌面打包 |
| 状态 | Zustand | 适合小型本地应用，减少样板代码 |
| 持久化 | IndexedDB + Dexie | 支持结构化数据和自动保存 |
| 渲染 | HTML/CSS | 文本可选中，适合 ATS 和打印 |
| PDF | 浏览器/Chromium 打印 | 与预览使用同一套 DOM/CSS |
| 校验 | Zod | 导入 JSON 时提供清晰错误信息 |
| Markdown 导入 | remark + 自定义映射 | 一次性脚本，产出条目池 JSON |
| 测试 | Vitest + Playwright | 覆盖数据逻辑和关键用户流程 |

## 3. 数据层原则

### 池 + 组合，而非补丁

内容只存一份，放在条目池中。「一份简历长什么样」由一个组合对象描述：选了哪些区块、哪些条目、哪些 bullet，以及它们的顺序。

主简历和岗位版本使用同一种组合结构。岗位版本只存与主简历不同的 key。

```text
render(pool, master, variant)
  = resolveComposition(master, variant.composition)
  + applyTextOverrides(variant.textOverrides)
```

这里没有通用的 patch/merge 引擎。绝大多数针对 JD 的调整是「选什么、什么顺序」，用选择清单就能表达；只有个人简介、条目标题和 bullet 文本需要文字覆盖，且是整值替换而非文本 diff。

### 继承粒度

`resolveComposition` 按 key 回退，粒度决定了主简历的更新能流到哪里：

| 组合字段 | 回退粒度 | 含义 |
|---|---|---|
| `sectionOrder` / `visibleSections` | 整体 | 版本调过区块顺序或显隐后，主简历新增区块不会自动进入 |
| `sectionTitles` | 每个 `SectionId` | 版本重命名过某区块，该区块保持自己的名字；其他区块跟随主简历 |
| `entrySelection` | 每个 `SectionId` | 版本调过某区块的条目，主简历向该区块新增条目不会自动进入；其他区块照常继承 |
| `bulletSelection` | 每个 `EntryId` | 版本调过某条目的 bullet，主简历向该条目新增 bullet 不会自动进入；其他条目照常继承 |

未继承的情况不是静默丢失，而是产生 `upstream-changed` 提示，由用户决定是否接受。粒度可以做得更细，但代价是状态复杂度上升；先按上表实现，用真实使用检验是否够用。

### 区块是数据，不是模板里的硬编码

区块定义存在条目池里，包含 `kind`（决定用哪个渲染器）、`title`（默认名，可被覆盖）、`layout`（列表型或纯文本型）和 `removable`。模板按 `sectionOrder` 遍历区块并按 `kind` 分派渲染器，不写死区块的种类和顺序。

自定义区块只是 `kind: "custom"` 的区块，走通用渲染器。这样新增自定义区块不需要改模板代码。

内置区块的 `removable` 为 `false`：可以隐藏和重命名，但不能删除。删除按钮不出现比出现后报错更好。

### M1 只做主简历，但结构不简化

第一个里程碑只有一份主简历，没有素材池 UI 也没有岗位版本。**数据结构仍按池 + 组合建**：条目存在池里，主简历持有一份选择清单，新建的条目自动进入该清单。

这不是过度设计。反过来做的代价是确定的：用扁平数组直接建模一份简历，等到要加版本时，稳定 ID、bullet 独立寻址和选择清单三样都得补，等于重写数据层，而已经录入的真实内容还要迁移。按目标结构建，M2 不需要动数据形状——`ResumeVariant` 和 `workspaceSchema` 在 M1 就已完整，加岗位版本不需要 schema 迁移。

但要说清楚 M2 的实际成本，避免被这句话误导：**省下来的是数据形状，不是接线。** M1 结束时
`resolveComposition` 的生产调用者是 0（只有测试文件调它），`textOverrides` 从未被写入过，
两个 reducer 的每一条命令都硬编码写 `workspace.master`。所以 M2 的主要工作量在写路径——
让每条命令知道自己在写哪一份，并按下面的粒度表做 copy-on-write。

同理，`ResumeVariant` 的类型在 M1 就定义，只是没有实例。

### 文本内容与条目内容走同一条路

内容一律存在池里：条目的标题、bullet 的文本、文本型区块的正文（`Section.text`）。组合只负责「选了哪些、什么顺序」，覆盖只负责「这个版本把哪段文字换成了什么」。

因此渲染模型里 `RenderSection` 既有 `entries`，也有 `text`：`layout: "entries"` 的区块用前者，`layout: "text"` 的用后者。缺了 `text` 的话文本型区块渲染出来是空的——这是 issue #2 实现时暴露出的契约缺口。

### 稳定 ID

区块、条目和 bullet 都必须有稳定 ID。选择和排序全部按 ID 引用，不使用数组下标 —— 下标会在排序或删除后指向错误内容。

bullet 必须独立寻址，否则「本版本只展示这条经历下的两条 bullet」无法表达，而这是针对 JD 调整时最高频的操作。

### 条目池带来的简化

主简历「删除」一个条目 = 把它移出主简历的选择清单，条目本身留在池中。已选用它的岗位版本不受影响，因此不需要 `orphaned` 状态和对应的修复流程。

只有从池中彻底删除条目才会影响其他版本。这是唯一的破坏性操作，在确认对话框中列出使用该条目的版本。

### JSON 备份优先

JSON 是工作区的可迁移备份格式。IndexedDB 只是默认存储，不应成为唯一的数据出口。

## 4. 渲染与导出原则

- 编辑表单和简历预览共享同一份渲染模型；
- 预览使用真实文本和结构化 HTML；
- 打印样式独立定义 `@page`、页边距和分页规则；
- 默认单栏布局；
- 不使用 canvas 截图作为 PDF 主要内容；
- 模板与数据解耦，后续增加模板不需要重写编辑器。

### 预览上的区块操作

预览渲染时为每个区块容器打上 `data-section-id`，悬停时在容器内定位一个工具条（上移 / 下移 / 隐藏 / 重命名）。工具条只发出针对 `sectionOrder`、`visibleSections`、`sectionTitles` 的命令，不参与布局计算，因此对分页没有影响。

不做预览内自由拖拽：跨页拖放需要在分页容器之间做命中检测和落点指示，与分页实现强耦合，成本远高于收益。左栏列表的拖拽排序不受此限制，那是一个普通的扁平列表。

### 分页：测量式，屏幕与打印共用同一套页容器

预览要按真实分页显示，因此渲染管线从一开始就要面对分页，不能等到打磨阶段。

**CSS 多列已被实测排除**：Chromium 打印时列不映射成 PDF 页，无论内容多长都只产出一页。纯 CSS 的 `break-inside: avoid` / `orphans` / `widows` 只影响断点位置，本身不会把内容切成离散的页容器。

实际方案是测量式：

1. 模板把 `RenderModel` 摊平成不可分割的 block —— 基本信息、每个区块标题、每个条目、文本型区块的正文；
2. 在隐藏容器里按页内容宽排版，读回每个 block 的真实高度；
3. 贪心装进固定尺寸的页容器，区块标题与其后的第一个内容块绑定，避免标题落单；
4. 打印侧只做一件事：每个页容器加 `break-after: page`。

**屏幕页与打印页出自同一个容器序列**，不是两套机制凑一致。这是这个设计的全部价值——两者从结构上就不可能漂移，`docs/MVP-PRD.md` §10 的「预览内容与导出 PDF 内容一致」因此是结构保证，而不是需要反复回归的巧合。

### 测量式分页的三条硬约束

这三条一旦违反，失败方式都是**静默的**：分页结果错了，但没有任何东西报错。测试全绿，PDF 也照样导得出来，只是断在了不该断的地方。

**1. block 根元素必须零 margin，间距一律走 padding。** 测量读的是 `getBoundingClientRect()`，它不含外边距，也不会体现相邻元素的 margin 折叠。根元素带 margin 的 block，测出来的高度会小于它在真实文档流里占的高度，于是每页都会多塞一点，越往后偏得越多。

**2. 测量必须在字体加载完成之后进行。** 当前只用系统字体，没有这个问题。将来引入 webfont 时，必须在测量前加一道 font-load 门，否则会按回退字体的度量分页，字体换上后行数变化而页边界不变。

**3. 测量容器与页容器的排版上下文必须完全一致。** 这一条是实现 #4 时真实撞上的：编辑器外层加了一句 `font-family: system-ui`，级联进离屏测量容器，把页容器实际使用的字体换掉，页边界整体偏移，四条分页断言同时失败。

注意故障源不在分页代码里，也不在模板里，而在**一个跟分页毫无关系的组件的样式**上。任何一个把预览包起来的新组件都可能再次触发，而且没有任何提示。

因此这一条不能靠「记得别在祖先上写字体样式」这种约定来守。测量容器和页容器要显式共享同一个排版根：影响布局的字体属性（`font-family`、`font-size`、`font-weight`、`line-height`、`letter-spacing`、`word-spacing`、`font-stretch`）在两处都必须被同一套规则显式设定，而不是双双继承自不确定的祖先。

配套的闸是一条回归测试：取测量容器里的一个 block 和页容器里的同一个 block，断言二者上述属性的 computed 值逐项相等。谁再往祖先上加字体样式，这条测试就会红，而不是等到分页悄悄偏掉才发现。

### 约定与闸的分界

上面三条里，第 1 条目前只有 `template.css` 顶部的注释在守，第 2 条暂时不适用，第 3 条应该有测试。

这个分布本身说明问题：**注释是最弱的一档**，它提醒得了「注意别加 margin」，提醒不了「你刚加的这个组件的样式会级联到哪里」。等有第二个模板时，第 1 条应该做成跨模板的对比测试。在那之前，新增模板或新增包裹预览的组件时，这一节是必须过一遍的清单。

### 分页正确性写成测试

给定固定夹具，在真实浏览器里断言页数和每页首末条目的 `data-entry-id` 具体值，避免样式改动后无声退化。页数取自 DOM 页容器数量，并另有一条断言把它与 `page.pdf()` 实际产出的 PDF 页数对齐。

## 5. 版本与主简历的关系变更

主简历内容更新且岗位版本已调整过同一处时：

1. 版本内容保持不变，不被覆盖；
2. 对应位置标记 `upstream-changed`；
3. 界面提示主简历此处有更新；
4. 用户可选择接受更新，或保留当前版本内容并消除提示。

判断依据是组合对象的 key 归属，不做文本级 diff。

**不要用时间戳，也不要用内容哈希。** `Entry` / `Bullet` / `Section` 上都没有 `updatedAt`
（只有 `ResumeVariant` 有），主简历的编辑也不写任何时间戳，所以「主简历比变体新」这个比较根本做不出来；
而在 reducer 里读时钟会破坏「reducer 是纯函数、id 由 action 注入」这条既有约定。哈希则只能回答
「变了没」，回答不了「变了什么」，于是「接受更新」退化成整体覆盖，用户自己排的顺序全丢，
提示很快会被学会忽略。

做法是三方合并的 base：变体为每个**被它覆盖过的 key** 存一份「覆盖时主简历的值」。
`upstream-changed` 的判定是纯集合运算——新增 = `master[K] − baseline[K]`，删除 = `baseline[K] − master[K]`。
它是纯数据、无时钟、JSON 天然往返，可以在领域层用固定夹具完整测试。

两个容易做错的地方：继承中（未被覆盖）的内容改了**不需要任何提示**，它本来就该自动流进变体，
别对整个池做变更检测；`baseline` 里可能留有池中已不存在的悬空 ID（schema 故意接受悬空 ID），
差分逻辑必须容忍，且不能因此误报「有新增」。

## 6. 本地优先约束

MVP 不引入：

- 用户账号；
- 必需的 API 服务；
- 远程数据库；
- 默认开启的分析服务；
- 依赖网络才能完成的导出流程；
- 需要后台进程的通知与定时任务。

投递追踪的提醒在应用打开时计算并展示，不依赖系统通知。

如果未来加入 AI，必须作为显式的可选能力，并清楚显示哪些内容会离开本机。

## 7. Markdown 导入（推迟到 M4）

结论先记下，实现放到最后：

- 一次性单向导入，不做双向同步。应用在导入后成为唯一数据源，原 markdown 文件保留为历史存档。双写会立刻引入冲突检测与合并，是不必要的复杂度；
- 实现为独立脚本，输入 markdown，输出符合 schema 的工作区 JSON，再走正常 JSON 导入路径。导入逻辑不进入应用运行时，脚本可以随素材库结构反复调整重跑。

推迟的理由：手工录入一次的成本是固定的几小时，而在 schema 尚未被真实使用检验过时写导入器，会随结构调整反复返工。等 M1–M3 结构稳定后再写，一次到位。
